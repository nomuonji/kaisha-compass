# Kaisha Compass — CMS補足解説の編集方針

**適用範囲:** My Portal Public CMS `kaisha-compass` の `/features/` だけ。既存の15場面、資料要約、原典・領域、章順、階層UIは引き続きGitHubが正本。CMS記事がその仕組みを代替・更新したと主張しない。

## この媒体の仕事
「会社の一年で、どんな用事が突然発生し、次に何を確認・決定・提出するのか」を理解できる補足教材にする。法律用語の辞書やニュースを量産するのではなく、読者が会社の具体的な場面に戻って判断の順番を把握できる記事を選ぶ。

**必要性が先、検索需要はその後。** 実務上の締切、手続の順序、解雇・雇用、請求・支払、税・社会保険、役員決定、契約など、会社を続けていくと避けて通れない局面を見つける。企業一般の薄い「コツ」やAIによる法務まとめは不採用。

## 企画と執筆
1. 既存の会社の一年から**一つの場面**を特定し、「この時点で読者が実際に困ること／選択しなければならないこと」を一文で書く。既存章や資料要約で完結していれば追加しない。
2. 公式の行政資料・法令・公的手続案内に当たる。対象者、要件、時点、例外、必要書類、期限、次に確認する相手を、確認した範囲で明示する。資料を読めないときは断定して公開しない。
3. 会社の登場人物・時系列を一つの**通し事例**として使用し、問題→確認事項→判断・手順→結果・例外の順に組む。事例は「説明のための架空例」と明示し、実際の経験に見せかけない。
4. 公式原典を開く前に、何が書かれ何の判断に使えるかを本文内で説明する。外部リンクだけを渡して終了しない。
5. 既存の0概要→1場面→2領域→3資料要約→4原典のレベルを混ぜない。CMS記事は**別レイヤーの補足解説**で、記事中に該当する場面・領域への参照を出す場合も、リンクの行き先が分かる呼称を使う。

## 知性と文体
会社という日常の制度には、実際に起こる妙な順序や「なぜここでこの書類が要るのか」という違和感がある。これに気づける視点は歓迎する。しかし、タイトル・見出し・手順・法的判断にボケや詩的言い回しを挟む必要はない。**面白さは説明する対象の選び方と発見に置き、文章は明快にする。**

見出しは「何をいつ決めるか」「誰が提出するか」「どの時点の制度か」のような機能的な日本語。『原典を開かなくても分かる』『30秒で』など説明を妨げるコピーは使わない。専門用語を一度だけ定義し、DBカード羅列ではなく順に読める文章とする。

## 掲載判断
**採用**：実際に起こる局面・意思決定が特定され、既存15場面を補う、一次情報と適用日を確認した、読後に次の確認手順が分かる。
**改稿**：一般論が先に長い、実行順序が見えない、場面とのリンクが曖昧、資料の紹介だけ、根拠と例外の境界が曖昧。
**没・保留**：制度確認できない、特定案件の結論を一般化する、架空の実体験、公式資料を読んだふり、会社経営のポエム、宣伝目的の比較記事。

## 成果と境界
成果は公開本数でなく、**実務上の判断迷いを何件減らす説明ができたか**（代理指標：手順明確性、法令根拠、適用時点、場面との接続、既存教材との重複回避）。法令改正時は無理な加筆より適用日を更新・保留する。
Sites OperatorはSEO・サイト技術、GitHubは固定教材を管理。Agent HQは`/features/`の企画・制作・改稿のみ。公開はMy Portal CMSの編集承認・privacy scan・publish・読み戻しを要する。

**運用必須:** 現行`AGENTS.md`、`docs/EDITORIAL_POLICY.md`、`docs/UX_DECISIONS.md`、`docs/PORTAL_CMS_CONTRACT.md`を読み、サイトの読書順・階層・原典の扱いを壊さない。
